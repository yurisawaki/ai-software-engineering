## Etapa 1 — Serviço antropométrico

Foi criado:

```text
app/Services/AnthropometricMeasurementService.php
```

O serviço centraliza as regras relacionadas aos dados antropométricos.

Principais responsabilidades:

* cálculo do IMC;
* validação dos arrays utilizados pelo contrato legado;
* validação de datas;
* validação de altura e peso;
* tratamento de payload vazio para preservar a semântica existente de limpar o histórico.

O cálculo do IMC utiliza uma casa decimal e retorna `null` para valores inválidos.

## Etapa 2 — Persistência e API legada

O fluxo passou a:

1. validar o payload;
2. somente depois alterar os registros;
3. executar delete + insert dentro de uma transação;
4. realizar rollback caso ocorra uma falha;
5. preservar o contrato existente da API.

O contrato legado foi mantido:

# Etapa 4 — Exportação

A próxima lacuna identificada foi o exportador.

Atualmente, a view:

```text
public.exporter_student_grouped_registration
```

já obtém `height` e `weight` através do registro antropométrico mais recente.

Porém, o exportador ainda não disponibilizava:

* data da medição;
* IMC.

Foi feita uma investigação antes de implementar essa etapa.

### Descobertas

A view utiliza um `LEFT JOIN LATERAL` sobre:

```text
pmieducar.aluno_historico_altura_peso
```

selecionando a medição mais recente.

A arquitetura de versionamento das views utiliza o trait:

```text
App\Support\Database\AsView
```

e arquivos SQL versionados em:

```text
database/sqls/views/
```

Foi identificada a migration planejada:

```text
database/migrations/2026_09_22_104038_update_view_student_grouped_registration.php
```

Os arquivos envolvidos na Etapa 4 são:

```text
database/sqls/views/public.exporter_student_grouped_registration.sql
database/sqls/views/public.exporter_student_grouped_registration-2026-09-22.sql
database/migrations/2026_09_22_104038_update_view_student_grouped_registration.php
app/Models/Exporter/Student.php
tests/Unit/View/Exporter/StudentTest.php
NOTES.md
```

### Regra definida para o exportador

A medida mais recente continuará sendo utilizada.

O exportador deverá disponibilizar:

```text
height
weight
measurement_date
bmi
```

O IMC será derivado:

```text
peso / altura²
```

com uma casa decimal.

Não será criada uma coluna persistida de IMC.

Também será preservado o grain atual da view, evitando transformar o exportador em um histórico completo de medições.

### Cuidados definidos

Não alterar:

* API;
* `Aluno.js`;
* formulário de cadastro;
* ficha médica;
* fluxo de persistência;
* Dockerfile preexistente;
* testes existentes fora do escopo.

Também não serão corrigidas falhas do baseline apenas para fazer a Etapa 4 passar.

A migration deverá possuir `up` e `down`, sendo o `down` responsável por restaurar a versão anterior da view.

### Estado atual

A Etapa 4 foi investigada e o plano de implementação foi definido.

A migration ainda não foi validada no banco.

A implementação autorizada deverá:

1. atualizar a view;
2. atualizar o model/exporter;

A regressão completa será realizada somente depois que os testes específicos da Etapa 4 estiverem verdes.
